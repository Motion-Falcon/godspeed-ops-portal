13. EMPLOYMENT AGREEMENT (JOBSEEKER ONBOARDING)
--------------------------------------------------------------------------------
Trigger A:     A jobseeker's profile is created by a recruiter (auto-created
               consent record + email sent inline during profile creation)
API Endpoint:  POST /api/profile/submit
Trigger File:  server/src/routes/profile.ts

Trigger B:     A jobseeker logs in / accesses the portal for the first time
               and the system finds no existing employment agreement record
               (creates the record on-demand and sends the email)
API Endpoint:  GET /api/consent/jobseeker-onboarding-consent
Trigger File:  server/src/routes/consent.ts

Email Service: SendGrid (sgMail.send directly, inline in route handler)
Template File: server/src/email-templates/employment-agreement-html.ts

Recipients:
  TO: Jobseeker's email address
      - Trigger A: profileData.email (from profile creation payload)
      - Trigger B: req.user.email (authenticated jobseeker's email)

Subject:
  "Action Required: Sign Your Employment Agreement"

Content:
  - Heading: "Your Account Has Been Verified!"
  - Greeting: "Hello {recipientName},"
  - Green confirmation box: "Email Verification Complete — Your account has
    been successfully verified."
  - Explanation that the Employment Agreement must be signed before accessing
    the account
  - Option 1 — Sign Directly:
      CTA button: "Review & Sign Agreement" → {CLIENT_URL}/consent?token={consent_token}
      (unique token per jobseeker)
  - Option 2 — Sign via Account:
      CTA button: "Log In to Your Account" → {CLIENT_URL}/login
  - Next steps list: Sign agreement → Complete profile → Use portal
  - Warning: link is unique and must not be shared; account is inaccessible
    until agreement is signed
  - Signed: "The {PORTAL_NAME} Team"

Notes:
  - Requires the "employmentAgreement" template to exist in
    consent_document_templates table with is_active=true
  - If the template is not found, the email is silently skipped (profile
    creation still succeeds)
  - Email failure does NOT abort the parent operation in either trigger
  - Each jobseeker gets exactly one consent record
    (idempotent — existing record is reused on subsequent GET calls)
  - Trigger B only fires on the FIRST call per jobseeker (when no record
    exists); subsequent calls return the existing record without re-sending

================================================================================
  EMAIL FLOW ARCHITECTURE
================================================================================

  Two patterns are used for sending emails:

  PATTERN A — emailNotifier middleware (routes: profile, positions, timesheets,
               consent):
    1. Route handler executes and sets res.locals with data
    2. After response finishes (res 'finish' event), the emailNotifier
       middleware reads res.locals and req.body to build email data
    3. Email is sent asynchronously AFTER the HTTP response is already sent
    4. Failures are logged but do NOT cause the API response to fail

  PATTERN B — Direct sgMail.send() inside route handler (routes: timesheets
               send-email, invoices send-email, user resend-invitation):
    1. Email sending is part of the main request handler
    2. The HTTP response is only returned AFTER the email attempt completes
    3. Failures cause the API to return a 500 error response
